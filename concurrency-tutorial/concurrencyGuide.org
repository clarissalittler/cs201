* Goals of this document
What you're reading is a guide to concurrency and parallelism in Unix-like systems. We're going to work through processes, threads, synchronization, and inter-process communication (IPC) with lots of practical C examples. By the end of this, you should be comfortable writing programs that do multiple things at once — and more importantly, writing them /correctly/.

* Introduction to Concurrency
** What is concurrency?
So what do we mean when we say "concurrency"? Basically, it's when a system is juggling multiple tasks that overlap in time. This can happen through different mechanisms — processes, threads, or asynchronous I/O — and it's one of the most important (and tricky!) concepts in systems programming.

Now here's the thing that trips people up: concurrency doesn't necessarily mean things are executing /simultaneously/. It just means that progress is being made on multiple tasks, possibly by interleaving their execution. Your computer might be rapidly switching between tasks so fast that it /looks/ simultaneous, but there's a real difference between that and true parallelism.

** Why is concurrency important?
Okay, so why should you care about this? A few reasons:
- Better resource utilization — your CPU shouldn't be sitting idle waiting for a disk read to finish
- Responsiveness — nobody wants a UI that freezes while it's doing work in the background
- Servers need to handle multiple clients at once — you can't just serve one person at a time!
- It lets you actually use those multiple cores in your processor
- A lot of real-world problems are just naturally concurrent

** Concurrency vs. Parallelism
People use these interchangeably all the time, but they actually mean different things:

- *Concurrency* is about /dealing with/ multiple things at once — interleaving tasks, switching between them, making progress on all of them
- *Parallelism* is about /doing/ multiple things at once — literally executing on multiple CPU cores simultaneously

I like to think of it this way: concurrency is one cook working on three dishes by switching between them. Parallelism is three cooks each working on their own dish. You can have concurrency without parallelism (one core, time-slicing) and you can have parallelism without much concurrency design (embarrassingly parallel problems). But most of the time in practice you're dealing with both.

* Processes
** What is a process?
A process is basically a running instance of a program. When you type =ls= at the command line, that creates a process. When you open your web browser, that's a process. Each process gets its own:
- Address space (its own chunk of memory)
- Program counter (where it is in the code)
- Register set
- Stack and heap
- File descriptors
- Signal handlers

The key thing about processes is that they're /isolated/ from each other. One process can't just reach into another process's memory. This is great for stability — if one process crashes, it doesn't take the rest of the system down with it — but it also means that getting processes to /talk/ to each other requires some extra work (which we'll cover in the IPC section).

** Process Creation: fork()
In Unix-like systems, processes are created with the =fork()= system call, and it's one of the weirdest things you'll encounter if you're coming from a normal programming background. When a process calls =fork()=, the operating system /clones/ the entire process. Now you have two nearly identical processes running the same code from the same point. Wild, right?

The way you tell them apart is through the return value of =fork()=:
- In the *parent* process: =fork()= returns the PID (process ID) of the new child
- In the *child* process: =fork()= returns 0
- If something went wrong: =fork()= returns -1

*** Basic fork example
#+begin_src c
#include <stdio.h>
#include <unistd.h>

int main() {
    pid_t pid = fork();
    
    if (pid < 0) {
        // Fork failed
        perror("Fork failed");
        return 1;
    } else if (pid == 0) {
        // Child process
        printf("Child process: My PID is %d, my parent's PID is %d\n", 
               getpid(), getppid());
    } else {
        // Parent process
        printf("Parent process: My PID is %d, my child's PID is %d\n", 
               getpid(), pid);
    }
    
    return 0;
}
#+end_src

*** Key points about fork()
Some things to keep in mind:
- After =fork()=, both parent and child continue from the exact same point in the code (the instruction right after the =fork()= call)
- The child gets /copies/ of the parent's stuff: file descriptors, signal handlers, environment variables, current working directory, resource limits
- Memory is "copy-on-write" for efficiency — the OS doesn't actually duplicate all the memory until one of the processes tries to modify it
- Variables with the same names exist in both processes but they're completely separate copies — changing one doesn't affect the other

** Process Execution: exec family
So =fork()= gives you a copy of the current process, but what if you want to run a /different/ program? That's what the =exec= family is for. These functions replace the current process's code with a completely new program. The process keeps its PID and other attributes, but it's now running entirely different code.

There are several variants (the naming is a bit of a mess, honestly):
- =execl()=: Arguments as a list
- =execv()=: Arguments as a vector (array)
- =execle()=: List of arguments plus custom environment
- =execve()=: Vector of arguments plus custom environment

The classic Unix pattern is =fork()= + =exec()=: fork a child, then immediately exec a new program in the child. That's literally how your shell runs every command you type!

Example:
#+begin_src c
#include <stdio.h>
#include <unistd.h>

int main() {
    pid_t pid = fork();
    
    if (pid == 0) {
        // Child process
        printf("Child about to execute ls command...\n");
        execl("/bin/ls", "ls", "-l", NULL);
        // The following will only execute if execl fails
        perror("execl failed");
        return 1;
    } else if (pid > 0) {
        // Parent process
        printf("Parent created child with PID %d\n", pid);
    }
    
    return 0;
}
#+end_src

** Process Termination and Waiting
Processes can end their life in a few ways:
- Returning from =main()=
- Calling =exit()= (or =_exit()= if you're in a child process after =fork()= and want to avoid flushing the parent's I/O buffers — this is a subtle but real gotcha!)
- Getting killed by a signal (like SIGTERM or SIGKILL)

When a child process terminates, the parent should collect its exit status. If the parent doesn't, the child becomes a "zombie" (more on that in a moment). You collect the status with:
- =wait()=: Waits for /any/ child to finish
- =waitpid()=: Waits for a /specific/ child

Example:
#+begin_src c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    pid_t pid = fork();
    
    if (pid == 0) {
        // Child process
        printf("Child executing...\n");
        sleep(2);
        exit(42);  // Exit with status 42
    } else {
        // Parent process
        int status;
        printf("Parent waiting for child...\n");
        waitpid(pid, &status, 0);
        
        if (WIFEXITED(status)) {
            printf("Child exited with status %d\n", WEXITSTATUS(status));
        }
    }
    
    return 0;
}
#+end_src

** Zombie and Orphan Processes
Two fun (well, "fun") terms you'll hear:
- *Zombie process*: A child that has finished executing but its parent hasn't called =wait()= yet. The child's entry sticks around in the process table, just holding its exit status, taking up space. It's "dead" but not fully gone. If you keep leaking zombies, you'll eventually run out of process table entries, which is bad.
- *Orphan process*: A child whose parent has terminated before it. The child doesn't just disappear — it gets "adopted" by the init process (PID 1), which will eventually call =wait()= on it. So orphans are actually handled pretty gracefully by the OS.

* Threads
** What are threads?
If processes are like separate apartments (each with their own kitchen, bathroom, etc.), threads are more like roommates sharing the same apartment. Threads exist /within/ a process and share most of that process's resources:
- The same address space (code, data, heap — all shared!)
- Open file descriptors
- Signal handlers

But each thread gets its own:
- Thread ID
- Program counter (they can be at different points in the code)
- Register set
- Stack (each thread needs its own call stack)

This sharing is both the strength and the danger of threads. Sharing memory makes communication between threads trivially easy — you just read and write the same variables. But it also means threads can stomp all over each other's data if you're not careful. That's where synchronization comes in (which we'll get to shortly).

** Thread Creation: pthread_create()
On Linux (and most Unix-like systems), we use POSIX threads, usually just called "pthreads". It's the standard API for creating and managing threads in C. You'll need to include =<pthread.h>= and compile with the =-pthread= flag (e.g., =gcc -pthread program.c -o program=).

Basic thread creation:
#+begin_src c
#include <stdio.h>
#include <pthread.h>

void* thread_function(void* arg) {
    printf("Thread executing with argument: %s\n", (char*)arg);
    return NULL;
}

int main() {
    pthread_t thread;
    char* message = "Hello from main thread";
    
    // Create a new thread
    if (pthread_create(&thread, NULL, thread_function, message) != 0) {
        perror("Thread creation failed");
        return 1;
    }
    
    // Wait for thread to complete
    pthread_join(thread, NULL);
    printf("Thread joined\n");
    
    return 0;
}
#+end_src

** Thread Termination and Joining
Threads can end by:
- Returning from their thread function (the most normal way)
- Calling =pthread_exit()= explicitly
- The entire process exiting (which kills all its threads)

When a thread finishes, you usually want to "join" it — this is like =wait()= for threads:
- =pthread_join()=: Blocks until the specified thread finishes, then collects its return value
- =pthread_detach()=: If you don't care about joining a thread, you can detach it. Its resources will be cleaned up automatically when it finishes. You can't join a detached thread.

** Thread vs Process: when do you use which?
This comes up a lot, and there's no single right answer — it depends on what you need.

*** Threads are great when you need:
- Fast creation and teardown (much cheaper than processes)
- Easy data sharing between tasks (it's just shared memory!)
- Low overhead (threads share the address space, so less memory duplication)

*** Processes are great when you need:
- Isolation — if one task crashes, you don't want it to take everything else down
- Security — processes can't read each other's memory
- Simplicity — you don't have to worry about shared-state bugs

A good rule of thumb: if your tasks need to share a lot of data and you trust the code, use threads. If your tasks are independent or you're running untrusted code, use processes. Many real-world systems (like web browsers) use both.

* Thread Synchronization
** The Need for Synchronization
So here's where things get interesting — and by "interesting" I mean "the source of some of the worst bugs you'll ever encounter." When multiple threads can read and write the same data, you get *race conditions*: the output of your program depends on the exact timing of how threads interleave. And since thread scheduling is non-deterministic, these bugs can be maddeningly hard to reproduce.

Synchronization is how we impose order on this chaos.

** Race Condition Example
Let's look at the classic example. Say two threads both want to increment a shared counter:
#+begin_src c
// race_condition.c — compile with: gcc -pthread race_condition.c -o race_condition
#include <stdio.h>
#include <pthread.h>

int counter = 0;

void* increment(void* arg) {
    (void)arg;
    for (int i = 0; i < 1000; i++) {
        counter++; // This is not atomic!
    }
    return NULL;
}

int main() {
    pthread_t thread1, thread2;

    pthread_create(&thread1, NULL, increment, NULL);
    pthread_create(&thread2, NULL, increment, NULL);

    pthread_join(thread1, NULL);
    pthread_join(thread2, NULL);

    // Expected: 2000, but will often be less due to the race condition
    printf("Final counter value: %d (expected 2000)\n", counter);
    return 0;
}
#+end_src

Here's the problem: =counter++= /looks/ like a single operation, but it's actually three steps at the machine level:
1. Read the current value of counter from memory
2. Add 1 to it
3. Write the new value back to memory

If two threads execute this at the same time, they might both read the same value (say, 5), both increment it to 6, and both write 6 back. You just lost an update! Run this with two threads doing 1000 increments each and you'll get some number less than 2000.

** Mutexes (Mutual Exclusion)
The most basic synchronization tool is the *mutex* (short for "mutual exclusion"). A mutex is like a lock on a bathroom door: only one thread can hold it at a time. If another thread tries to lock an already-locked mutex, it blocks until the first thread unlocks it.

The pattern is always the same: lock, do your critical work, unlock. Keep the critical section as small as possible — you're making every other thread wait!

Basic mutex usage:
#+begin_src c
#include <stdio.h>
#include <pthread.h>

int counter = 0;
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

void* increment(void* arg) {
    (void)arg;
    for (int i = 0; i < 1000; i++) {
        pthread_mutex_lock(&mutex);
        counter++;  // Critical section
        pthread_mutex_unlock(&mutex);
    }
    return NULL;
}

int main() {
    pthread_t thread1, thread2;
    
    pthread_create(&thread1, NULL, increment, NULL);
    pthread_create(&thread2, NULL, increment, NULL);
    
    pthread_join(thread1, NULL);
    pthread_join(thread2, NULL);
    
    printf("Final counter value: %d\n", counter);
    return 0;
}
#+end_src

*A note on atomics:* For simple operations like incrementing a counter, C11 provides atomic types (=_Atomic int counter;= from =<stdatomic.h>=) that avoid the need for a full mutex. Atomic operations use hardware support (like the =lock= prefix on x86) and are much faster than mutex lock/unlock cycles. But they only work for simple, single-variable operations — anything more complex still needs a mutex.

** Condition Variables
Sometimes a thread needs to wait until something specific happens before it can proceed. You /could/ do this by repeatedly checking a flag in a loop (called "busy waiting"), but that wastes CPU cycles. Condition variables give you a much better option: a thread can go to sleep and be woken up when the condition it cares about becomes true.

Condition variables always work together with a mutex. The pattern is:
1. Lock the mutex
2. Check if your condition is true
3. If not, call =pthread_cond_wait()= — this atomically releases the mutex and puts the thread to sleep
4. When woken up, the mutex is re-acquired and you check the condition again (always use a =while= loop, not =if=, because of spurious wakeups!)

Example:
#+begin_src c
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
int ready = 0;

void* producer(void* arg) {
    (void)arg;
    pthread_mutex_lock(&mutex);

    // Do some work to produce data
    printf("Producer: Working...\n");
    sleep(2);
    
    // Set the condition and signal
    ready = 1;
    printf("Producer: Data is ready!\n");
    pthread_cond_signal(&cond);
    
    pthread_mutex_unlock(&mutex);
    return NULL;
}

void* consumer(void* arg) {
    (void)arg;
    pthread_mutex_lock(&mutex);

    // Wait until data is ready
    while (!ready) {
        printf("Consumer: Waiting for data...\n");
        pthread_cond_wait(&cond, &mutex);
    }
    
    // Process the data
    printf("Consumer: Processing data\n");
    
    pthread_mutex_unlock(&mutex);
    return NULL;
}

int main() {
    pthread_t prod_thread, cons_thread;
    
    pthread_create(&cons_thread, NULL, consumer, NULL);
    pthread_create(&prod_thread, NULL, producer, NULL);
    
    pthread_join(prod_thread, NULL);
    pthread_join(cons_thread, NULL);
    
    return 0;
}
#+end_src

** Semaphores
A semaphore is like a bouncer with a counter. It keeps track of how many "slots" are available. =sem_wait()= decrements the counter (and blocks if it would go below zero), and =sem_post()= increments it (and wakes up a waiting thread if any).

Semaphores are useful for two things:
- *Binary semaphores* (counter of 0 or 1): essentially a mutex, but with different semantics — notably, a different thread can "unlock" a semaphore than the one that "locked" it
- *Counting semaphores*: controlling access to a pool of resources (e.g., "up to 5 database connections")

The classic example is the producer-consumer problem with a bounded buffer:

#+begin_src c
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

#define MAX_ITEMS 10
#define BUFFER_SIZE 5

sem_t empty;
sem_t full;
sem_t mutex;
int buffer[BUFFER_SIZE];
int in = 0, out = 0;

void* producer(void* arg) {
    (void)arg;
    for (int i = 0; i < MAX_ITEMS; i++) {
        int item = i + 1;
        
        sem_wait(&empty);  // Wait for empty slot
        sem_wait(&mutex);  // Enter critical section
        
        buffer[in] = item;
        printf("Producer: Inserted item %d at position %d\n", item, in);
        in = (in + 1) % BUFFER_SIZE;
        
        sem_post(&mutex);  // Exit critical section
        sem_post(&full);   // Signal item produced
    }
    return NULL;
}

void* consumer(void* arg) {
    (void)arg;
    for (int i = 0; i < MAX_ITEMS; i++) {
        sem_wait(&full);   // Wait for an item
        sem_wait(&mutex);  // Enter critical section
        
        int item = buffer[out];
        printf("Consumer: Removed item %d from position %d\n", item, out);
        out = (out + 1) % BUFFER_SIZE;
        
        sem_post(&mutex);  // Exit critical section
        sem_post(&empty);  // Signal slot emptied
    }
    return NULL;
}

int main() {
    pthread_t prod_thread, cons_thread;
    
    sem_init(&empty, 0, BUFFER_SIZE);  // Buffer starts empty
    sem_init(&full, 0, 0);             // Buffer starts with no items
    sem_init(&mutex, 0, 1);            // Binary semaphore for CS
    
    pthread_create(&prod_thread, NULL, producer, NULL);
    pthread_create(&cons_thread, NULL, consumer, NULL);
    
    pthread_join(prod_thread, NULL);
    pthread_join(cons_thread, NULL);
    
    sem_destroy(&empty);
    sem_destroy(&full);
    sem_destroy(&mutex);
    
    return 0;
}
#+end_src

** Deadlocks
A deadlock is what happens when threads get stuck waiting for each other in a cycle. Thread A holds lock 1 and is waiting for lock 2. Thread B holds lock 2 and is waiting for lock 1. Neither can make progress. They'll sit there forever.

For a deadlock to happen, you need /all four/ of these conditions at once:
1. *Mutual exclusion*: The resources can't be shared (only one thread at a time)
2. *Hold and wait*: A thread holds one resource while waiting for another
3. *No preemption*: You can't forcibly take a resource away from a thread
4. *Circular wait*: There's a cycle in the waiting graph

Example (this code will deadlock!):
#+begin_src c
// deadlock.c — compile with: gcc -pthread deadlock.c -o deadlock
// WARNING: This program will likely deadlock! Use Ctrl+C to kill it.
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

pthread_mutex_t mutex1 = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_t mutex2 = PTHREAD_MUTEX_INITIALIZER;

void* thread1_function(void* arg) {
    (void)arg;
    pthread_mutex_lock(&mutex1);
    sleep(1);  // Increases chance of deadlock
    pthread_mutex_lock(&mutex2);

    // Critical section
    printf("Thread 1: acquired both mutexes\n");

    pthread_mutex_unlock(&mutex2);
    pthread_mutex_unlock(&mutex1);
    return NULL;
}

void* thread2_function(void* arg) {
    (void)arg;
    pthread_mutex_lock(&mutex2);
    sleep(1);  // Increases chance of deadlock
    pthread_mutex_lock(&mutex1);

    // Critical section
    printf("Thread 2: acquired both mutexes\n");

    pthread_mutex_unlock(&mutex1);
    pthread_mutex_unlock(&mutex2);
    return NULL;
}

int main() {
    pthread_t thread1, thread2;

    pthread_create(&thread1, NULL, thread1_function, NULL);
    pthread_create(&thread2, NULL, thread2_function, NULL);

    pthread_join(thread1, NULL);
    pthread_join(thread2, NULL);

    printf("Both threads completed successfully (no deadlock occurred)\n");
    return 0;
}
#+end_src

The fix? Break any one of those four conditions. In practice, the easiest approaches are:
- *Lock ordering*: Always acquire locks in the same global order. If everyone always locks =mutex1= before =mutex2=, you can't get a cycle.
- *Lock timeouts*: Use =pthread_mutex_timedlock()= and back off if you can't get the lock
- *Avoid holding multiple locks*: Redesign your code so you never need two locks at once

* Inter-Process Communication (IPC)
** What is IPC?
Remember how I said processes are isolated from each other? That's great for safety, but eventually processes need to /talk/ to each other. That's what IPC (Inter-Process Communication) is for. Since processes don't share memory by default, you need explicit mechanisms to pass data between them. Unix gives you several options, each with different trade-offs.

** Pipes
Pipes are the simplest IPC mechanism. You've probably already used them at the command line: =ls | grep foo= creates a pipe between =ls= and =grep=. In C, =pipe()= creates a pair of file descriptors — one for reading, one for writing. Data flows in one direction only (write end to read end).

Pipes work between related processes (parent-child), because the child inherits the pipe's file descriptors from the parent via =fork()=.

Example:
#+begin_src c
#include <stdio.h>
#include <unistd.h>
#include <string.h>
#include <sys/wait.h>

int main() {
    int pipefd[2];  // pipefd[0] is read end, pipefd[1] is write end
    pid_t pid;
    char message[] = "Hello from the parent!";
    char buffer[100];

    if (pipe(pipefd) == -1) {
        perror("pipe");
        return 1;
    }

    pid = fork();

    if (pid == -1) {
        perror("fork");
        return 1;
    } else if (pid == 0) {  // Child process
        close(pipefd[1]);  // Close unused write end

        read(pipefd[0], buffer, sizeof(buffer));
        printf("Child received: %s\n", buffer);

        close(pipefd[0]);
    } else {  // Parent process
        close(pipefd[0]);  // Close unused read end

        write(pipefd[1], message, strlen(message) + 1);

        close(pipefd[1]);
        wait(NULL);  // Wait for child to finish
    }

    return 0;
}
#+end_src

** Named Pipes (FIFOs)
Regular pipes only work between related processes (since the child has to inherit the file descriptors). Named pipes, also called FIFOs, solve this — they exist as special files in the filesystem, so /any/ process can open them by name.

Example (writer):
#+begin_src c
#include <stdio.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <unistd.h>
#include <string.h>

int main() {
    int fd;
    char message[] = "Hello via FIFO!";
    
    // Create the named pipe (FIFO)
    mkfifo("/tmp/myfifo", 0666);
    
    // Open the FIFO for writing
    fd = open("/tmp/myfifo", O_WRONLY);
    
    // Write to the FIFO
    write(fd, message, strlen(message) + 1);
    
    // Close the FIFO
    close(fd);
    
    return 0;
}
#+end_src

Example (reader):
#+begin_src c
#include <stdio.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <unistd.h>

int main() {
    int fd;
    char buffer[100];
    
    // Open the FIFO for reading
    fd = open("/tmp/myfifo", O_RDONLY);
    
    // Read from the FIFO
    read(fd, buffer, sizeof(buffer));
    printf("Received message: %s\n", buffer);
    
    // Close the FIFO
    close(fd);
    
    return 0;
}
#+end_src

** Message Queues
Message queues let processes send structured messages to each other. Unlike pipes (which are just byte streams), message queues preserve message boundaries — each =msgsnd()= sends a discrete message that's received as a whole unit by =msgrcv()=. Messages also have a type field, which lets you selectively receive specific message types.

Note: this example uses the older System V message queue API. There's also a POSIX message queue API (=mq_open=, etc.) that's more modern, but System V is still widely used and is what you'll see in a lot of existing code.

Example:
#+begin_src c
#include <stdio.h>
#include <sys/ipc.h>
#include <sys/msg.h>
#include <string.h>

// Message structure
struct msg_buffer {
    long msg_type;
    char msg_text[100];
};

int main() {
    key_t key = ftok("progfile", 65);
    int msgid = msgget(key, 0666 | IPC_CREAT);
    struct msg_buffer message;

    // Sender
    message.msg_type = 1;
    strcpy(message.msg_text, "Hello from message queue!");
    // Note: size should be the size of the data only (excluding msg_type)
    msgsnd(msgid, &message, sizeof(message.msg_text), 0);

    // Receiver (in real applications, this would be in a different process)
    msgrcv(msgid, &message, sizeof(message.msg_text), 1, 0);
    printf("Received: %s\n", message.msg_text);

    // Destroy the message queue
    msgctl(msgid, IPC_RMID, NULL);

    return 0;
}
#+end_src

** Shared Memory
Shared memory is the fastest IPC mechanism because there's no copying — both processes are literally reading and writing the same physical memory. The downside? You're back to all the shared-state problems we discussed in the threading section. You'll need to use semaphores or some other synchronization to avoid races.

Example:
#+begin_src c
#include <stdio.h>
#include <sys/ipc.h>
#include <sys/shm.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    key_t key = ftok("shmfile", 65);
    int shmid = shmget(key, 1024, 0666|IPC_CREAT);
    char *str = (char*) shmat(shmid, NULL, 0);

    // Write before forking — both processes share the memory,
    // so the child will see the data immediately
    strcpy(str, "Hello from shared memory!");
    printf("Parent wrote message to shared memory\n");

    if (fork() == 0) {  // Child process
        printf("Child read: %s\n", str);
        shmdt(str);
    } else {  // Parent process
        wait(NULL);  // Wait for child
        shmdt(str);
        shmctl(shmid, IPC_RMID, NULL);  // Destroy shared memory
    }

    return 0;
}
#+end_src

Sockets are the heavy-duty IPC mechanism — they're how processes talk to each other over a network /and/ on the same machine. Everything you do on the internet involves sockets at some level: web browsers, email, SSH, you name it.

* Common Concurrency Patterns
** Producer-Consumer
The producer-consumer pattern is probably the most common concurrency pattern you'll encounter. The idea is simple: one or more threads produce data and put it in a shared buffer, and one or more threads consume data from that buffer. You need synchronization to make sure producers don't overflow the buffer and consumers don't read from an empty one. We already saw this in the semaphore section — that bounded-buffer example /is/ the producer-consumer pattern.

** Reader-Writer
The reader-writer pattern comes up when you have data that's read much more often than it's written. Multiple threads can safely read at the same time (since reads don't modify anything), but writes need exclusive access. A reader-writer lock (=pthread_rwlock_t=) gives you exactly this: multiple concurrent readers OR one exclusive writer, but never both.

** Thread Pool
Creating a new thread for every task is wasteful — thread creation isn't free. A thread pool solves this by keeping a fixed set of worker threads alive, waiting for tasks to arrive in a queue. When a task comes in, an idle worker picks it up. When it's done, the worker goes back to waiting. This is how most web servers and application frameworks handle concurrency under the hood.

Here's a simplified implementation to give you the idea:
#+begin_src c
// Simplified thread pool example
#include <stdio.h>
#include <pthread.h>
#include <stdlib.h>
#include <unistd.h>

#define POOL_SIZE 3
#define QUEUE_SIZE 10

// Task structure
typedef struct {
    void (*function)(void*);
    void* argument;
} Task;

// Thread pool structure
typedef struct {
    Task taskQueue[QUEUE_SIZE];
    int front, rear, count;
    pthread_t workers[POOL_SIZE];
    pthread_mutex_t queueMutex;
    pthread_cond_t queueNotEmpty;
    pthread_cond_t queueNotFull;
    int shutdown;
} ThreadPool;

ThreadPool* pool;

// Worker thread function
void* worker(void* arg) {
    while (1) {
        pthread_mutex_lock(&pool->queueMutex);
        
        // Wait for work if queue is empty
        while (pool->count == 0 && !pool->shutdown) {
            pthread_cond_wait(&pool->queueNotEmpty, &pool->queueMutex);
        }
        
        // Exit if shutting down and queue is empty
        if (pool->shutdown && pool->count == 0) {
            pthread_mutex_unlock(&pool->queueMutex);
            pthread_exit(NULL);
        }
        
        // Get task from queue
        Task task = pool->taskQueue[pool->front];
        pool->front = (pool->front + 1) % QUEUE_SIZE;
        pool->count--;
        
        // Signal that queue is not full anymore
        pthread_cond_signal(&pool->queueNotFull);
        pthread_mutex_unlock(&pool->queueMutex);
        
        // Execute task
        (*(task.function))(task.argument);
    }
    
    return NULL;
}

// Initialize thread pool
void threadPoolInit() {
    pool = (ThreadPool*)malloc(sizeof(ThreadPool));
    pool->front = pool->rear = pool->count = 0;
    pool->shutdown = 0;
    
    pthread_mutex_init(&pool->queueMutex, NULL);
    pthread_cond_init(&pool->queueNotEmpty, NULL);
    pthread_cond_init(&pool->queueNotFull, NULL);
    
    // Create worker threads
    for (int i = 0; i < POOL_SIZE; i++) {
        pthread_create(&pool->workers[i], NULL, worker, NULL);
    }
}

// Add task to thread pool
void threadPoolAdd(void (*function)(void*), void* argument) {
    pthread_mutex_lock(&pool->queueMutex);
    
    // Wait if queue is full
    while (pool->count == QUEUE_SIZE) {
        pthread_cond_wait(&pool->queueNotFull, &pool->queueMutex);
    }
    
    // Add task to queue
    Task task = {function, argument};
    pool->taskQueue[pool->rear] = task;
    pool->rear = (pool->rear + 1) % QUEUE_SIZE;
    pool->count++;
    
    // Signal that queue is not empty
    pthread_cond_signal(&pool->queueNotEmpty);
    pthread_mutex_unlock(&pool->queueMutex);
}

// Shutdown thread pool
void threadPoolShutdown() {
    pthread_mutex_lock(&pool->queueMutex);
    pool->shutdown = 1;
    pthread_mutex_unlock(&pool->queueMutex);
    
    // Wake up all worker threads
    pthread_cond_broadcast(&pool->queueNotEmpty);
    
    // Wait for all worker threads to finish
    for (int i = 0; i < POOL_SIZE; i++) {
        pthread_join(pool->workers[i], NULL);
    }
    
    // Clean up
    pthread_mutex_destroy(&pool->queueMutex);
    pthread_cond_destroy(&pool->queueNotEmpty);
    pthread_cond_destroy(&pool->queueNotFull);
    
    free(pool);
}
#+end_src

* Best Practices
** General Concurrency Guidelines
After wrestling with all of the above, here's the hard-won wisdom:
1. *Keep critical sections small* — the less code under a lock, the less contention
2. *Minimize shared data* — the less shared state, the fewer bugs. Seriously, this one is huge.
3. *Use higher-level abstractions when possible* — if a library provides a thread-safe queue, use it instead of rolling your own mutex-guarded list
4. *Understand and avoid race conditions* — if you can't reason about why your code is safe, it probably isn't
5. *Use thread-safe functions* — many C standard library functions (=strtok=, =localtime=, etc.) are NOT thread-safe. Use their =_r= variants.
6. *Be aware of deadlocks* — whenever you hold more than one lock, think about ordering
7. *Prefer message passing over shared memory when appropriate* — it's easier to reason about
8. *Test extensively* — and know that passing tests doesn't mean your concurrent code is correct. It might just mean you got lucky with the scheduling.

** Debugging Concurrent Programs
Debugging concurrent programs is genuinely hard. Here's why:
- Bugs are often *non-deterministic* — they depend on timing, so they might happen 1 in 1000 runs
- Traditional debugging (stepping through code) *changes the timing*, which can make bugs disappear (this is called a "Heisenbug" and yes, the name is intentional)
- Race conditions can be practically impossible to reproduce on demand

Techniques that actually help:
- *Logging with thread/process IDs* — when something goes wrong, you need to reconstruct what happened and in what order
- *ThreadSanitizer* (compile with =-fsanitize=thread=) — this is genuinely magical. It instruments your code to detect data races at runtime. Use it!
- *Helgrind* (a Valgrind tool) — similar idea, different implementation
- *Assertions* — sprinkle =assert()= calls to check invariants. If a race condition violates one, you'll know immediately instead of getting silently corrupted data

** Performance Considerations
A few things to keep in mind as you write concurrent programs:
1. *Too many threads is a thing* — if you have 1000 threads on 8 cores, you're spending most of your time context switching instead of doing work
2. *Locking isn't free* — every =pthread_mutex_lock= has overhead. If your critical section is tiny, the lock might cost more than the work it protects
3. *False sharing is sneaky* — if two threads modify different variables that happen to be on the same cache line (typically 64 bytes), the CPU has to keep bouncing that cache line between cores, destroying performance
4. *Think about granularity* — locking once per 1000 items is better than locking once per item. But a single giant lock defeats the purpose of multithreading. Find the balance.
