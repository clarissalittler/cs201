** Files and file I/O
 + We've already used read and write from assembly
 + 0 is stdin, 1 is stdout, 2 is stderr
 + A file descriptor is a number referring to an entry in a process's descriptor table
 + =fdStandard.c=: run it with =>=, =2>=, and a pipe -- who decided what 0, 1, and 2 are?
** Let's copy a file
 + =fdCat.c=
 + =argc= and =argv= for the filename (=argv.c= if we need a refresher)
 + =open=, =read=, =write=, =close=
 + Run it first, then walk through it
 + (=openfile1.c=, =readfile1.c=, =writefile1.c= are smaller steps toward it)
** What does read return?
 + Positive: this many bytes
 + Zero: end of file
 + -1: an error
 + This is a byte count, not a string length
 + The buffer doesn't have to contain text or a terminating zero
** Why are there two loops?
 + Read until EOF
 + Write until we've sent all the bytes from that read (=writeAll= in =fdCat.c=)
 + Suppose write only writes three bytes
   + Where should the next write start?
   + How many bytes remain?
 + Interrupted calls and real errors
** Everything is a file (descriptor)
 + The same copy loop on very different things:
   + =./fdCat /proc/cpuinfo=, =./fdCat /dev/null=, =echo hi | ./fdCat /dev/stdin=
   + =./fdCat /etc= (a directory) and =./fdCat nope.txt=
 + =fdDevices.c=: =/dev/urandom=, =/dev/zero=, =/dev/null= are drivers, not data
 + =fdTable.c=: files, pipes, and devices in one descriptor table
   + =/proc/self/fd= lets us look at our own table
   + Which number does the next =open= get? (=openfile2.c= opens the same file over and over)
 + Always redirect to a /new/ output file; redirecting onto the input would erase it first
** Pipes and redirection are just descriptor tricks
 + =fdPipe.c=: a pipe is a file with no name
   + EOF only when /every/ write end is closed -- what happens if we forget one?
 + =fdRedirect.c=: =dup2= then =exec= is how the shell does =ls -l > listing.txt=
