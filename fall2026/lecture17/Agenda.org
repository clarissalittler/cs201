* Agenda
** Part 1: TCP, one conversation at a time
*** Internet sockets!
 + Files gave us a descriptor we could read and write
 + Now the bytes are going to another program
 + We're using TCP
*** Addresses and ports
 + Remember byte order from the start of the term?
 + Host byte order vs. network byte order
 + =htons=, =htonl=, =ntohs=, =ntohl=
*** A server that accepts one connection
 + =step1HelloOnce.c=
 + =socket=, =bind=, =listen=, =accept=
 + There are /two/ descriptors to keep straight
   + The listening socket
   + The accepted connection
 + Start it with a port number: =./step1HelloOnce 5000=
 + Connect with =nc -d 127.0.0.1 5000=
 + It sends a fixed message, hangs up, and exits
 + Connect again: "Connection refused", nobody's listening any more
*** TCP gives us a stream of bytes
 + It doesn't preserve our application's message boundaries
 + One send doesn't necessarily correspond to one recv
 + Part of a line might arrive, then the rest
 + We still need the short-transfer loop from the file lectures
   + The step examples skip it so the socket calls stand out
*** When the client goes away
 + Read/recv returns zero at EOF
   + That's how =step3EchoLoop.c= knows to close and go back to =accept=
 + A send can fail if the other end has closed
 + =MSG_NOSIGNAL= keeps that failed send from terminating the server with SIGPIPE
 + The step servers bind =INADDR_ANY=, so they accept connections on any of this machine's addresses, not just loopback
*** Accepting another connection
 + Where would the outer loop go?
 + =step2HelloLoop.c= moves =accept= into a loop
   + =diff step1HelloOnce.c step2HelloLoop.c=
 + =step3EchoLoop.c= echoes, but a second client waits for the first
 + =step4EchoPoll.c= and =step5EchoSelect.c= serve many clients at once
 + =step6Client.c= shows the other side of the conversation
*** A step-by-step server progression
 + [[file:SocketSteps.md][SocketSteps.md]] has the walkthrough and =nc= commands for each step
 + Each step changes as little as possible: =diff= neighbouring files
 + =step1HelloOnce.c=: one =accept=, a fixed message, then exit
   + =nc -d 127.0.0.1 PORT= (=-d=: quit when the server hangs up)
 + =step2HelloLoop.c=: =accept= in a loop, one client after another
 + =step3EchoLoop.c=: echo until the client hangs up
   + =nc -N 127.0.0.1 PORT= (=-N=: Ctrl-D tells the server we're done)
   + Connect two clients: the second waits for the first
 + =step4EchoPoll.c=: =poll()= so many clients can talk at once
 + =step5EchoSelect.c=: the same server written with =select()=
 + =step6Client.c=: our own client that works with all five
   + It needs =poll()= too: keyboard /and/ socket
*** Other kinds of sockets
 + Change the arguments to =socket()= and the program keeps the same shape
 + =udpEcho.c=: =SOCK_DGRAM= instead of =SOCK_STREAM=
   + No =listen=, no =accept=: one socket, and every datagram says who sent it
   + =recvfrom= / =sendto=
   + =nc -u 127.0.0.1 PORT=
 + =udpSend.c one two three=: three datagrams arrive as three =recvfrom=s
   + Message boundaries are kept, unlike TCP
   + Stop the server: =sendto= still "works" and nobody tells us
 + =unixEcho.c=: =AF_UNIX= instead of =AF_INET=
   + The address is a file name: =ls -l echo.sock=
   + =nc -U -N echo.sock=
   + Never touches the network: IPC between programs on one machine
   + The kernel tells us the client's pid and uid
 + =socketPair.c=: two connected sockets, no name, shared with =fork=
   + A pipe that goes both ways

** Part 2: From echo to the web-server project
*** Where we are
 + A TCP connection gives us a stream of bytes
 + Now let's give those bytes a meaning
*** One thread per client
 + [[file:../../assignments/assignment4-scaffold/httpd.c][The final-project scaffold]]
 + Follow the accepted descriptor into the worker
 + Remember the thread-argument problem with passing the address of a changing variable?
 + Each client gets its own allocated slot
 + Who frees that slot? Who closes the socket?
 + =echoServerThread.c= is another look at the handoff, with some rough edges
*** A very small HTTP response
 + Status line
 + Headers
 + A blank line
 + The body
 + =Content-Length= counts /bytes/
 + Start with fixed text and look at it with =curl -v=
*** From a response to a file server
 + Read the request line
 + Map / to /index.html
 + Look for the file inside www
 + Send the right content type and length
 + =webServer.c= and =webClient.c= are reference examples
 + The scaffold leaves the request handling for you to implement
*** What if the file isn't there?
 + A 404 response is still a response
 + Binary files aren't strings
 + Keep the parsing bounded and keep track of actual byte counts
 + The client can disconnect partway through
 + Even a request that fits our buffer may take more than one read
