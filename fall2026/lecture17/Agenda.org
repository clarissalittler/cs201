* Agenda
** Part 1: TCP, one conversation at a time
*** Internet sockets!
 + Files gave us a descriptor we could read and write
 + Now the bytes are going to another program
 + We're using TCP
*** Addresses and ports
 + Remember byte order from the start of the term?
 + Host byte order vs. network byte order
 + =htons=, =htonl=, =ntohs=, =ntohl=
*** A server that accepts one connection
 + =echo_once.c=
 + =socket=, =bind=, =listen=, =accept=
 + There are /two/ descriptors to keep straight
   + The listening socket
   + The accepted connection
 + Start it with port 0 to have the system choose a port
 + Connect with =nc 127.0.0.1 PORT=
 + Type something and get it back
*** TCP gives us a stream of bytes
 + It doesn't preserve our application's message boundaries
 + One send doesn't necessarily correspond to one recv
 + Part of a line might arrive, then the rest
 + We still need the short-transfer loop from the file lectures
*** When the client goes away
 + Read/recv returns zero at EOF
 + A send can fail if the other end has closed
 + =MSG_NOSIGNAL= keeps that failed send from terminating this Linux example with SIGPIPE
 + This example listens on loopback and serves one connection, then exits
*** Accepting another connection
 + Where would the outer loop go?
 + =echoServerLoop.c= shows the basic change, with less error handling
 + =echoClient.c= shows the other side of the conversation
 + The select/poll examples are under optional if you'd like to look ahead

** Part 2: From echo to the web-server project
*** Where we are
 + A TCP connection gives us a stream of bytes
 + Now let's give those bytes a meaning
*** One thread per client
 + [[file:../../assignments/assignment4-scaffold/httpd.c][The final-project scaffold]]
 + Follow the accepted descriptor into the worker
 + Remember the thread-argument problem with passing the address of a changing variable?
 + Each client gets its own allocated slot
 + Who frees that slot? Who closes the socket?
 + =echoServerThread.c= is another look at the handoff, with some rough edges
*** A very small HTTP response
 + Status line
 + Headers
 + A blank line
 + The body
 + =Content-Length= counts /bytes/
 + Start with fixed text and look at it with =curl -v=
*** From a response to a file server
 + Read the request line
 + Map / to /index.html
 + Look for the file inside www
 + Send the right content type and length
 + =webServer.c= and =webClient.c= are reference examples
 + The scaffold leaves the request handling for you to implement
*** What if the file isn't there?
 + A 404 response is still a response
 + Binary files aren't strings
 + Keep the parsing bounded and keep track of actual byte counts
 + The client can disconnect partway through
 + Even a request that fits our buffer may take more than one read
